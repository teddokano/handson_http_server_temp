1. Zephyrとは？

 

 

1.1 Zephyrの概要と特長

 

Zephyrは，Linux Foundation配下で開発が進むオープンソースのRTOS（リアルタイムOS）です．小規模なマイコンから，比較的リソースの大きなSoCまで，幅広いハードウェアを対象にしています．

対象範囲の広さは，NXP製品だけを見ても分かります．今回使うMCXシリーズのようなCortex-Mコアのマイコンから，i.MXシリーズのようなCortex-Aコアのアプリケーションプロセッサまで，同じZephyrという1つのOSでカバーしています．ボードごとにOSやビルド環境を使い分けなくて済むのは，実用上の大きなメリットです．

特長を一言でまとめると，次の2つの仕組みで，ハードウェアの構成とソフトウェアの機能を分けて管理できる点です．

  • デバイスツリー: 「どの部品が，どこにつながっているか」というハードウェアの構成を書くファイル
  • Kconfig: 「どの機能を使うか」というソフトウェアの機能のオン・オフを設定する仕組み

この分離のおかげで，同じアプリケーションのコードを，複数のボードに展開しやすくなっています．

言い換えると，C言語などで書くアプリケーションのロジックは，「何のセンサーが」「どのバスに」つながっているかを直接知らなくてよい，という設計です．アプリケーションのコードは，デバイスツリーに付けた名前を使ってデバイスにアクセスするだけです．この分離を，2.4節と3.3節で実際のコードを見ながら体感します．

 

1.2 なぜ今Zephyrなのか

 

半導体メーカー各社が，既存製品ラインを含めZephyrへの対応を広げています．特定のベンダーに縛られないRTOSとして，業界内での存在感が増しているのが現状です．

Zephyrプロジェクトは2016年にLinux Foundation配下でスタートし，およそ10年の歴史を持ちます．新しくて枯れていない技術ではありません．

この間に積み重ねられてきたのは，CPUアーキテクチャやペリフェラルのドライバだけではありません．4章・5章で体験するTCP/IPスタックやHTTPサーバーといった，ネットワーク関連のミドルウェアも，Zephyr本体に標準で組み込まれた機能として育ってきています．マイコン向けOSというと，最小限のスケジューラだけを想像しがちです．こうした上位のミドルウェアまで，一貫してKconfigで有効にできる点も，Zephyrを選ぶ理由のひとつです．

製品に使うOSとして，セキュリティへの取り組みが整っていることも，Zephyrが注目される理由です．欧州では，ネットワークにつながる製品にサイバーセキュリティ対策を求める「サイバーレジリエンス法（CRA）」が施行され，2026年9月からは，悪用された脆弱性の報告がメーカーの義務になっています．Zephyrプロジェクトは，脆弱性への対応や長期サポートの体制を整え，こうした要求に応える準備を進めています（下のコラム）．

「結局何がそんなによいのか」は，触ってみないと実感しにくい部分です．この記事では，実際に手を動かしながらその感触を確かめていきます．

コラム: Zephyrのセキュリティへの取り組み

  • 脆弱性に対応する専門チーム（PSIRT）があり，2017年からCVE番号を割り当てる機関（CNA）に登録されています．報告を受けてから，30日以内にメーカーへの通知と修正の公開を，最長90日で公表することを目標にしています．
  • 製品メーカーは，脆弱性の通知（Vulnerability Alert Registry）に登録して，情報を受け取れます．
  • 製品向けの長期サポート版（LTS）は，セキュリティ修正を含めて少なくとも5年間保守されます．
  • west spdxで，製品に含まれるソフトウェアの一覧（SBOM）を作れます．
  • 暗号機能はPSA Crypto（実装はMbed TLS）で提供されます．FRDM-MCXN947には，TrustZoneを使うTF-Mと組み合わせるボード指定（frdm_mcxn947/mcxn947/cpu0/ns）も用意されています．

CRAとZephyrの関係は，Zephyrの公式ドキュメントのCyber Resilience Actのページにまとめられています．なお，このハンズオンでは手順を簡単にするため，暗号化しないプレーンHTTPを使っています（4.1節の解説）．

FRDM-MCXN947は，NXPのMCX N947マイコンを搭載した評価ボードです．150MHzで動作するCortex-M33のデュアルコア構成です．GPIO・I2C・I3C・SPI・Ethernetなどのペリフェラルを，ArduinoヘッダやmikroBusソケットなどのコネクタ経由で扱えます．

ステップ2: westを使える状態にする

westを使う前に，Zephyr用のPython仮想環境（Zephyrのツールをまとめて入れてある，独立したPythonの環境）を有効化し，Zephyr本体の場所を環境変数ZEPHYR_BASEに設定します．次のコマンド例をコピーして，PowerShellに貼り付けて実行してください．

  • PowerShellのウィンドウ上で右クリックするか，Ctrl+Vを押すと貼り付けられます．

注意: このPowerShellのウィンドウは閉じない

仮想環境の有効化やZEPHYR_BASEの設定は，そのウィンドウの中だけで有効です．セミナーの間は，このウィンドウを開いたままにしておいてください．閉じてしまったときは，下の「PowerShellを開き直したときは」の手順で戻れます．

うまくいかないときは

  • .\.venv\Scripts\Activate.ps1で「このシステムではスクリプトの実行が無効になっている」と赤字が出る → 下の解説の最後にある実行ポリシーの設定を行ってから，コマンド例2.1-1をもう一度最初から実行します．
  • westが「認識されません」と出る → 仮想環境の有効化に失敗しています．プロンプトの先頭に(.venv)が付いているか確認してください（A.2）．
  • cdで「パスが存在しないため検出できません」と出る → ワークスペースが~\zephyrproject以外の場所にある可能性があります．ご自身の環境で試している場合は，ワークスペースの場所に読み替えてください．

PowerShellを開き直したときは

新しいPowerShellで環境を設定し直してから，作業していたサンプルのフォルダに戻ります．会場のPCには，これを一度に行うzinitというコマンドを用意してあります．zinitに続けて，作業していたサンプルの名前を指定します．たとえば3章の途中なら，次のように実行します．

# コマンド例2.1-2 zinit thermometer

サンプル名は，途中まで入力してTabキーを押すと補完されます．サンプル名を付けずにzinitだけを実行すると，コマンド例2.1-1を実行した直後と同じ状態（~\zephyrprojectにいる状態）になります．zinitはVSCodeのターミナルでも使えます．

zinitがないPCでは，コマンド例2.1-1を実行してから，cd ~\handson\thermometerのようにサンプルのフォルダに移動します．コマンド例2.1-1を実行した直後は~\zephyrprojectにいるので，そのままwest buildを実行しても，サンプルのビルドにはなりません．

解説: コマンド例2.1-1で何をしているか

  • cd ~\zephyrproject — Zephyrのワークスペース（west・Zephyr本体・各種モジュールをまとめて置いてあるフォルダ）に移動します．
  • .\.venv\Scripts\Activate.ps1 — Zephyr用に用意されたPython仮想環境を有効化します．west自体やビルドに使う各種Pythonツールが，この仮想環境にインストールされています．有効化に成功すると，プロンプトの先頭に(.venv)と表示されます．
  • $env:ZEPHYR_BASE = "..." — Zephyr本体のフォルダを環境変数ZEPHYR_BASEに設定します．westは，カレントディレクトリから上のフォルダをたどってワークスペースを探します．この後の章では，ワークスペースの外にある作業用フォルダ（~\handson\...）でビルドします．そこからではワークスペースが見つからず，west buildが「unknown command」になってしまいます．ZEPHYR_BASEを設定しておくと，westはそれを手がかりにワークスペースを見つけられます．
  • west --version — westコマンド自体が正しく使える状態になっているかを，バージョン表示で確認します．
  • west topdir — westが認識しているワークスペースの場所を表示します．ここでエラーになる場合は，ZEPHYR_BASEの設定を見直してください．

Linux/macOSの解説記事では，source ~/zephyrproject/.venv/bin/activateやsource zephyr/zephyr-env.shという書き方をよく見かけます．これはbash/zsh用の書き方で，PowerShellではそのままでは動きません．

zephyr-env.shが主に行っているのは，ZEPHYR_BASEの設定です．そこでPowerShellでは，上のように$env:ZEPHYR_BASEで直接設定します．（Windows向けにはzephyr-env.cmdも用意されていますが，これはコマンドプロンプト用です．PowerShellから実行しても，設定した環境変数はPowerShell側には残りません．）

なお，Activate.ps1の実行時に「スクリプトの実行が無効になっている」というエラーが出る場合は，PowerShellの実行ポリシーで止められています．Set-ExecutionPolicy -Scope CurrentUser RemoteSignedを一度実行してから，もう一度試してください（会場PCでは設定済みです）．

コラム: コマンドをコピー＆ペーストするときの注意

  • 複数行の貼り付けの確認ダイアログ: Windows Terminalでは，複数行を貼り付けると「複数行のテキストを貼り付けようとしています」という確認が出ることがあります．そのまま貼り付けを選んでください．
  • 途中でエラーが出たら，そこで止まる: 複数行をまとめて貼り付けると，途中の行でエラーが出ても，後ろの行が続けて実行されてしまいます．赤い文字のエラーが出たら，それより後の結果は当てにせず，エラーが出た行の原因を先に解決してください．慣れないうちは，1行ずつコピーして実行するのが確実です．
  • # コマンド例…の行は目印: 質問するときや，付録Aを参照するときに，この番号を使ってください．
  • プロンプト（PS C:\Users\...>）はコピーしない: スクリーンショットや実行例に表示されているプロンプト部分は，コマンドの一部ではありません．

うまくいかないときは，記事末尾の付録A. うまくいかないときはを参照してください．記事中のコマンド例は，付録B. コマンド例一覧にもまとめています．macOSやLinuxで試す方向けのbash・zsh版もそちらに載せています．

コラム: ご自身のPCでzinitを使うには

zinitは，PowerShellのプロファイル（PowerShellの起動時に自動で読み込まれるスクリプト）に登録した関数です．ご自身のPCでも，次のようにして同じものを用意できます．

まず，次のコマンドでプロファイルをメモ帳で開きます（ファイルがなければ作ります）．

# コマンド例2.1-3 if (-not (Test-Path $PROFILE.CurrentUserAllHosts)) { New-Item -Force $PROFILE.CurrentUserAllHosts | Out-Null } notepad $PROFILE.CurrentUserAllHosts

開いたメモ帳に，次の内容を書き加えて保存します．これはPowerShellに貼り付けて実行するコマンドではなく，プロファイルに書く内容です．

function zinit { param([string]$Sample) Set-Location ~\zephyrproject . .\.venv\Scripts\Activate.ps1 $env:ZEPHYR_BASE = "$HOME\zephyrproject\zephyr" west --version west topdir if ($Sample) { Set-Location ~\handson\$Sample } }

保存したら，PowerShellのウィンドウを開き直すとzinitが使えるようになります．プロファイルの実行にも，この節の解説で説明した実行ポリシーの設定（RemoteSigned）が必要です．なお，プロファイルに日本語を書く場合は，文字コードに注意が必要です（Windows PowerShellは，BOMなしのUTF-8のファイルに含まれる日本語を正しく読めません）．上の内容は英数字だけなので，そのまま保存して構いません．

ご自身のPCで試す場合: 環境のセットアップ

今回は会場PCに環境構築済みの状態で臨んでいただいていますが，ご自身のPCでも同じ環境を用意できます．インストール方法は，0.3節の「ご自身のPCで再現する方へ」を参照してください．

解説: 作業用フォルダへのコピー（コマンド例2.2-1）

1行目のNew-Itemで，作業用フォルダ~\handsonを作っておきます（すでにある場合は何もしません．この行は最初の1回だけで大丈夫です）．Copy-Item -Recurseで，zephyr\samples\の中のサンプルをフォルダごと作業用フォルダにコピーし，cdでそのフォルダに移動しています．以降の章でも同じように，触りたいサンプルをまず作業用フォルダへコピーしてから作業を始めます．

Copy-Itemは，コピー先のフォルダがすでに存在すると，その中にサンプルのフォルダをもう1つ作ってしまいます（例: ~\handson\hello_world\hello_world）．コピーをやり直したいときは，先にRemove-Item -Recurse -Force ~\handson\hello_worldで古いフォルダを消してから実行してください．

解説: -b・-pオプション（コマンド例2.2-2）

  • -bに続く引数は，ビルド対象のボードの指定です．FRDM-MCXN947はCortex-M33のデュアルコア構成なので，frdm_mcxn947/mcxn947/cpu0のように「ボード名／SoC名／コア名」まで指定します．FRDM-MCXA153のようなシングルコアのボードでは，frdm_mcxa153というボード名だけで済みます．
  • SoC名を省略してfrdm_mcxn947//cpu0と書くこともできます．FRDM-MCXN947のようにSoCが1つしかないボードでは，間のSoC名を省いてスラッシュだけを残しても一意に決まるためです．本記事でも，2.3節以降はこの省略形を使います．
  • -p autoは--pristine=autoの省略形です．ビルドフォルダをクリーンな状態から作り直す（pristineビルドする）かどうかを，自動で判定します．詳しくは次の解説で説明します．
  • 以降の章で登場するwest build・west flashでも，これらのオプションの意味は同じです．

解説: ビルドでできたファイルの場所

ビルドが成功すると，カレントディレクトリにbuild/フォルダが作られます．書き込みに使われるのはbuild/zephyr/zephyr.elf（デバッグ情報付きのELFファイル）で，この後実行するwest flashも，このファイルをボードに書き込みます．そのほか，コンフィグの内容はbuild/zephyr/.config，展開後のデバイスツリーはbuild/zephyr/zephyr.dtsで確認できます．

--pristineは，このビルドフォルダを作り直すかどうかを指定するオプションです．-p auto（--pristine=auto）は，ソースやコンフィグの変更を検知して，必要なときだけビルドフォルダを作り直します．ビルドの様子がおかしいときなど，明示的にクリーンビルドしたい場合は-p always（--pristine=always）を指定します．

ご自身のPCで試す場合（Tera Term）

  • Tera Termの手順3と4の設定は，「設定」→「設定の保存」で保存しておくと，次回からは手順2だけで接続できます．
  • macOSやLinuxでは，Tera Termは使えません．CoolTermなどで，ポートに/dev/tty.usbmodemXXXX（macOS）や/dev/ttyACM0（Linux）を選び，ボーレートを115200にして接続してください．

hello_worldのコードを見てみる

hello_worldのsrc/main.cは，次のように驚くほど短いコードです．VSCodeでこのファイルを開くには，PowerShellからcode ~\handson\hello_world\src\main.cを実行します．（VSCodeの「Open Folder」でフォルダを開くと，記事を表示しているウィンドウの中身が切り替わってしまうので，会場では使わないでください．）

#include <stdio.h> int main(void) { printf("Hello World! %s\n", CONFIG_BOARD_TARGET); return 0; }

これを見る限り，至って普通のC言語によるHello Worldコードです．強いて特別な点を挙げるなら，CONFIG_BOARD_TARGETというマクロがこのビルド環境の中で定義されているのだろう，という程度です．マイコンプログラムでよく見られるクロック設定やペリフェラルの初期化処理は，このコードのどこにも見当たりません．

このコードには，「RTOSのコードっぽくなさ」もあります．タスク（スレッド）の生成も，スケジューラの起動もありません．main()からprintf()を呼ぶだけで，PC向けのC言語プログラムとほとんど同じ見た目です．

多くのRTOSでは，「Hello World」のためにもタスクを明示的に作り，osKernelStart()のような呼び出しでスケジューラを起動する必要があります．Zephyrでは，main()自体がすでに1つのスレッドとして動いています．その手前の初期化は，ビルドシステムとKconfigの設定に任されています．この「素のCプログラムに近い書き味」は，Zephyrがアプリケーション開発者に見せる顔の特徴のひとつです．

解説: main.c以外に必要なファイル

Zephyrアプリケーションとして最低限必要なのは，src/main.cのほかにprj.confとCMakeLists.txtの2つです．

  • prj.confは，そのアプリケーションで使うKconfigの機能を並べる設定ファイルです．hello_worldでは特に有効にしたい機能がないため，中身はほぼ空です．
  • CMakeLists.txtは，ビルドの定義ファイルです．find_package(Zephyr ...)でZephyrのビルドシステムを読み込み，target_sources()でビルドするソースファイルを指定します．

実際にzephyr/samples/hello_world/の中を見ても，ファイルはCMakeLists.txt・prj.conf・src/main.c（と説明用のREADME.rst）程度しかありません．Zephyrアプリケーションの最小構成は，この3点セットです．

2.4 サンプルコードの中身をちょっと覗いてみる

 

この節では，blinkyのコードを見ながら，LEDの場所がどこで決まっているのかを確かめます．

blinkyのsrc/main.cは，GPIOをトグル（出力を反転）するだけの短いコードです．全体を見てみましょう．VSCodeで開くには，PowerShellからcode ~\handson\blinky\src\main.cを実行します．

/* * Copyright (c) 2016 Intel Corporation * * SPDX-License-Identifier: Apache-2.0 */ #include <stdio.h> #include <zephyr/kernel.h> #include <zephyr/drivers/gpio.h> /* 1000 msec = 1 sec */ #define SLEEP_TIME_MS 1000 /* The devicetree node identifier for the "led0" alias. */ #define LED0_NODE DT_ALIAS(led0) /* * A build error on this line means your board is unsupported. * See the sample documentation for information on how to fix this. */ static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED0_NODE, gpios); int main(void) { int ret; bool led_state = true; if (!gpio_is_ready_dt(&led)) { return 0; } ret = gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE); if (ret < 0) { return 0; } while (1) { ret = gpio_pin_toggle_dt(&led); if (ret < 0) { return 0; } led_state = !led_state; printf("LED state: %s\n", led_state ? "ON" : "OFF"); k_msleep(SLEEP_TIME_MS); } return 0; }

上から順に，次のことをしています．

  • SLEEP_TIME_MSで，点滅の間隔（1000ミリ秒＝1秒）を決めています．
  • DT_ALIAS(led0)とGPIO_DT_SPEC_GET()で，led0という名前のLEDが，どのGPIOの何番ピンにつながっているかの情報（led）を取り出しています．
  • main()では，まずgpio_is_ready_dt()でGPIOが使えるか確かめ，gpio_pin_configure_dt()でそのピンを出力に設定します．
  • while (1)のループで，gpio_pin_toggle_dt()でLEDを反転し，printf()で状態を表示し，k_msleep()で1秒待つ，をくり返します．

ここで注目したいのは，コードのどこにも「どのピンにLEDがつながっているか」が書かれていないことです．コードが指定しているのは，led0というエイリアス（別名）だけです．led0が実際にどのLEDを指すのかは，Zephyr本体側にあるボードのデバイスツリー（ハードウェアの構成を書いたファイル．zephyr/boards/nxp/frdm_mcxn947/frdm_mcxn947.dtsi）で，次のように定義されています．

aliases { led0 = &red_led; ... }; red_led: led_3 { gpios = <&gpio0 10 GPIO_ACTIVE_LOW>; label = "Red LED"; };

（抜粋）

「led0はRGB LEDの赤（GPIO0の10番ピン）だ」という情報がボード側に書かれているので，アプリケーションはled0と言うだけで済みます．blinkyのフォルダには，FRDM-MCXN947向けの追加設定（boards/フォルダに置くオーバーレイ．ボードのデバイスツリーに差分を重ねるファイルで，3.3節で説明します）もありません．ボード側の定義だけで，そのまま動いているわけです．同じblinkyが，led0を定義しているどのボードでもそのまま動くのはこのためです．

アプリケーション・デバイスツリー・Kconfig・ドライバの関係を図にすると，図2.4-1のようになります．Kconfigは，Zephyrの機能のオン・オフを設定する仕組みです（3章でもう一度触れます）．

3.3 なぜ動いたのか？

 

この節では，センサーの値がなぜ表示されたのかを，src/main.cとboards/*.overlayを見ながら種明かしします．

main.c側では，センサーデバイスを次のように取得しています．

static const struct device *const temp_dev = DEVICE_DT_GET(DT_ALIAS(ambient_temp0));

このambient_temp0というエイリアスが，実際にどのハードウェア（センサーの品種・接続バス）を指すのかを決めているのが，boards/*.overlayです．オーバーレイは，ボード本体のデバイスツリーに，アプリケーションごとの差分を重ねるファイルです．

今回のFRDM-MCXN947では，温度センサーはI3Cバスにつながっています．boards/frdm_mcxn947_mcxn947_cpu0.overlayには，次のように定義されています（実際のファイルにはI3Cバスのクロック速度の指定なども含まれますが，ここでは要点を抜粋しています）．

/ { aliases { ambient-temp0 = &p3t1755; }; }; &i3c1 { status = "okay"; p3t1755: p3t1755@4800000236152a0090 { compatible = "nxp,p3t1755"; reg = <0x48 0x0236 0x152a0090>; status = "okay"; }; };

やっていることは2つだけです．

  • aliasesブロックで，ambient-temp0をp3t1755ノードに結び付ける
  • i3c1バスの下に，nxp,p3t1755ドライバを使うセンサーのノードを1つ追加する

main.c側はDT_ALIAS(ambient_temp0)としか書いていません．このセンサーがI2Cではなく（より高速な）I3Cでつながっていることも，レジスタアドレスの詳細も，アプリケーションのコードは一切知りません．

ここでの見どころは，「コードを一行も書かずに，デバイスツリーの定義を変えるだけで別のハードウェア構成に対応できる」ことです．たとえば，同じセンサーをI2C接続のボードに載せ替えたり，別の温度センサーIC（対応ドライバがある前提）に変えたりする場合を考えます．変更するのは基本的にboards/*.overlayの中だけで，main.cのDEVICE_DT_GET(DT_ALIAS(ambient_temp0))という1行はそのまま使い回せます．この関係を図にすると，図3.3-1のようになります．

図3.3-1：thermometerでの，アプリケーション・デバイスツリー・Kconfig・ドライバの関係

解説: デバイスツリーの実体はどこにあるのか

  1. FRDM-MCXN947のボード自体が持つデバイスツリーの本体は，Zephyr本体側のzephyr/boards/nxp/frdm_mcxn947/frdm_mcxn947_mcxn947_cpu0.dts（および共通定義のfrdm_mcxn947.dtsi）です．ここには，ボードに標準で載っているペリフェラル一式が定義されています．
  2. このボード本体のデバイスツリーファイルは，直接書き換えません．Zephyrでは，アプリケーション側に，ボード本体の定義へ追記・上書きするための差分ファイル（オーバーレイ，*.overlay）を置きます．
    thermometerではsamples/sensor/thermometer/boards/frdm_mcxn947_mcxn947_cpu0.overlay，5章で使うリポジトリではboards/frdm_mcxn947_mcxn947_cpu0.overlayです．本文で示したp3t1755ノードの定義も，このオーバーレイの中身です．ボード本体の定義はそのままに，アプリケーションごとに必要な差分だけを重ねられるのが利点です．
  3. ビルドすると，ボード本体のデバイスツリーとアプリケーションのオーバーレイがマージされ，最終的なデバイスツリー全体がbuild/zephyr/zephyr.dtsに書き出されます．このファイルを開くと，p3t1755ノードがボード本体の定義に追加されていることを確認できます．

OSを使わないベアメタル開発や，デバイスツリーの仕組みを持たない多くのRTOSでは，センサーのI2C/I3Cアドレスやレジスタ操作を，アプリケーションのコードの中に直接書くのが一般的です．そのため，センサーの型番やバスの配線が変わるたびに，アプリケーションのロジックを書き換える必要があります．Zephyrでは，「どの部品が」「どこに」つながっているかという情報をデバイスツリーという別の層に追い出しています．そのため，ボードが変わっても，アプリケーションのロジック（この場合は「気温を読んで表示する」という処理）そのものは触らずに済みます．

興味を持った方は，他のボード向けのoverlayファイルも見比べてみてください．同じsamples/sensor/thermometerでも，ボードごとにハードウェアの接続だけが違うoverlayが用意されていることが分かるはずです．

    2. prj.confのIPアドレスが192.168.1.100になっていて，保存されているか．保存し直した場合は，コマンド例4.1-3からビルドと書き込みをやり直します．
    3. シリアルコンソール（Tera Term）に，ボードの起動メッセージやIPアドレスの表示が出ているか．何も出ていなければ，RESETボタンを押してみます．
    4. それでもだめなら，A.6を参照してください．
  • 「宛先ホストに到達できません」と表示される → PC側のIPアドレスが192.168.1.xになっていない可能性があります（A.6）．

解説: なぜプレーンHTTPを使うのか

プレーンHTTPは，通信内容が暗号化されないHTTP通信です．実運用では，盗聴や改ざんを防ぐため，TLSで暗号化されたHTTPSの利用が推奨されます．HTTPSを使うには，サーバー証明書や秘密鍵といった認証まわりのファイルを，あらかじめ用意する必要があります．

Zephyrでも，こうした認証の仕組みや，通信を暗号化する仕組みはサポートされています．しかし今回のハンズオンでは，限られた時間の中で認証ファイルの準備を省き，HTTP Serverそのものの仕組みを体験することに集中するため，あえてプレーンHTTPを使います．

解説: Gatewayの設定について

Gateway（CONFIG_NET_CONFIG_MY_IPV4_GW）は，ルーターを経由しない通信では本来必須ではありません．今回はPCとボードをEthernetケーブルで直結し，同じ192.168.1.0/24のサブネットに両方を置きます．通信はすべて同一リンク内のARPで解決され，Gatewayを経由するルーティングは発生しません．そのため今回は，元の値のままでも，"192.168.1.1"に書き換えても，同じように動きます．

ボードをルーターにつないで別のネットワークと通信する場合は，そのルーターのアドレスに書き換える必要があります．

コラム: ネットワーク機能の「重さ」について

一般的な組み込み開発では，HTTPサーバーを1つ動かすだけでも，多くの下準備が必要になりがちです．TCP/IPスタック（lwIPなど）の組み込みと設定，ソケットAPIの用意，HTTPパーサーの選定と実装，静的ファイルの配信方法の実装，といった作業です．

今回は，それらがすべてprj.confのCONFIG_NET_*・CONFIG_HTTP_*系のオプションをyにするだけで揃っています．アプリケーション側で書いたのは，各エンドポイントのハンドラ関数（リクエストが来たときに呼び出される関数）だけです．ネットワークスタックからHTTPサーバーまでを，1つのビルドシステムとKconfigで一貫して扱える．これが，Zephyrがマイコン向けRTOSでありながら，比較的大きなミドルウェア込みで語られる理由のひとつです．

コラム: ZephyrのTCP/IPスタックはlwIPなのか

組み込み向けのTCP/IPスタックというと，lwIP（lightweight IP）を思い浮かべる方も多いかもしれません．しかしZephyrは，lwIPを外部から取り込むのではなく，subsys/net/以下に実装された独自のTCP/IPスタックを標準で使っています．IPv4/IPv6・TCP/UDP・ソケットAPIといった機能は，Zephyr本体に組み込まれています．

prj.confで有効にしているCONFIG_NET_IPV4やCONFIG_NET_TCP，CONFIG_NET_SOCKETSといったオプションも，このスタックの機能を指しています．（Zephyrは，モジュールとして外部のネットワークスタックを組み合わせる構成にも対応していますが，本記事で使っているのは標準のスタックです．）

 

4.3 /uptimeエンドポイントを覗いてみる

 

この節では，一番シンプルなエンドポイントの動きを確かめます．

✔ ここまでできればOK

この「GETリクエストに対して，値を計算してテキストで返す」というエンドポイントの作りを，次の5章でそのまま応用します．

解説: HTTPリクエストとレスポンス

  1. ブラウザで/uptimeにアクセスすると，ブラウザからボードへ，「このパスの内容をください」という意味のGETリクエストが送られます．
  2. ボード側では，リクエストを受け取ったHTTP Serverが，/uptimeに紐づけられたハンドラ関数（リクエストが来たときに呼び出される関数．ここではuptime_handler）を呼び出します．
  3. ハンドラは起動からの経過時間を計算し，その値をレスポンスの本文（body）としてセットします．
  4. HTTP Serverは，この本文にステータス行（200 OKなど）やヘッダーを付け加え，HTTPレスポンスとしてブラウザに返します．
  5. ブラウザは，受け取ったレスポンスの本文を画面に表示します．

5章で追加する/temperatureエンドポイントも，リクエストを受けて値を計算し，本文として返すという，まったく同じ流れで動いています．

  1. プロンプトの先頭に(.venv)が付いているか

  2. 今いるフォルダは正しいか

  3. 最初に出たエラーはどれか
    エラーが出ると後続のメッセージが大量に出ます．画面を上にスクロールして，最初に赤字やerrorが出た行を探してください．複数行をまとめて貼り付けた場合は，どのコマンドで最初にエラーが出たかを確認します．

# コマンド例A.1-1 Get-Location $env:ZEPHYR_BASE west topdir

ビルドが遅いとき（ご自身のPCで試している場合）

WindowsでのZephyrのビルドは，同じPCのLinuxより遅くなりがちです．http_serverのような大きめのサンプルでは，1回のビルドに数分かかることもあります．次の3つで大きく改善します（会場PCは設定済みです）．

  • ccacheを入れる: 一度コンパイルした結果を覚えておき，同じものを2回目以降は再利用するツールです．インストールしておけば，Zephyrが自動で使います．同じサンプルを同じフォルダでビルドし直すときは，-p alwaysでクリーンビルドした場合も含めて，コンパイルの大部分が省略されて速くなります（最初の1回は通常どおり時間がかかります）．筆者の環境では，http_serverのクリーンビルドが約4分半から73秒になりました．
  • Windows Defenderの除外設定: 「Windows セキュリティ」→「ウイルスと脅威の防止」→「設定の管理」→「除外」を開きます．~\zephyrproject・作業用フォルダ・Zephyr SDKのフォルダ・ccacheのキャッシュフォルダ（通常は%LOCALAPPDATA%\ccache）を，除外に追加します．Defender以外のウイルス対策ソフトを使っている場合は，そのソフトの設定で除外します．ビルドのたびに大量のファイルがスキャンされるのを防げます．会社のPCでは，情報システム部門の方針を確認してください．
  • 電源設定: ノートPCはACアダプタをつなぎ，電源モードを「最適なパフォーマンス」にします．
# コマンド例A.3-3 winget install --id Ccache.Ccache -e

bash・zshで試す場合の注意

  • パスの区切り: PowerShellの\は，bash・zshでは/になります．~がホームフォルダを表すのは共通です．
  • コマンド例の番号の行は付けていません: macOS標準のzshは，初期設定では対話中に入力した#をコメントとして扱いません．そのため# コマンド例2.1-1の行を貼り付けると「command not found: #」というエラーになります．bash・zsh版のコードブロックには番号の行を入れず，見出しで番号を示しています．
  • 仮想環境とZEPHYR_BASE: どちらもそのターミナルの中だけで有効なのは，PowerShellと同じです．ターミナルを開き直したら，コマンド例2.1-1から実行し直します．
  • シリアルポートの名前: macOSでは/dev/tty.usbmodemXXXX，Linuxでは/dev/ttyACM0などになります（2.2節）．

C.3 温度を華氏でも表示する

 

3章のthermometerで，摂氏（°C）に加えて華氏（°F）も表示してみましょう．

# コマンド例C.3-1 cd ~\handson\thermometer code src\main.c

main()の最後のほうにある，次の行を探します．

printf("Temperature is %0.1lf°C\n", sensor_value_to_double(&value));

ヒント: 華氏は「摂氏 × 9 ÷ 5 ＋ 32」で計算できます．

答えの例: 上の1行を，次の2行に置き換えます．

double c = sensor_value_to_double(&value); printf("Temperature is %0.1lf°C (%0.1lf°F)\n", c, c * 9.0 / 5.0 + 32.0);

保存したら，コマンド例3.1-2でビルド，コマンド例3.1-3で書き込みます．Temperature is 24.3°C (75.7°F)のように表示されれば成功です．

 

C.4 ブラウザに表示する温度の桁数を変える

 

5章の改変版HTTP Serverでは，温度を小数点以下3桁で表示しています．これを1桁にしてみましょう．

# コマンド例C.4-1 cd ~\handson\handson_http_server_temp code src\main.c

ヒント: 画面の表示に関わっているのは，main.cの中の次の2か所です．VSCodeの検索（Ctrl+F）で探してみてください．

  • temperature_handlerの中の，ページを最初に表示するときの書式: "Temperature: %.3f&deg;C"
  • 1秒ごとに表示を書き換えるJavaScriptの中: t.toFixed(3)

%.3fで検索すると，temperature_json_handlerの中にももう1か所見つかります．こちらはブラウザに数値を渡すためのものなので，今回は変えなくて構いません．

付録D. 他のFRDMボードで試すには

 

本記事はFRDM-MCXN947を前提にしていますが，ZephyrはNXPの他のFRDMボードにも対応しています．手元に別のボードがある場合のヒントをまとめます．

west buildの-bに指定するボード名は，次のコマンドで一覧できます．

# コマンド例D.1-1 west boards -n frdm_mcx

主なボードの指定方法は次のとおりです．

ボード -bに指定する名前

FRDM-MCXN236 frdm_mcxn236
FRDM-MCXA153 frdm_mcxa153
FRDM-MCXA156 frdm_mcxa156
FRDM-MCXC444 frdm_mcxc444

FRDM-MCXN947のようなデュアルコアのボード以外は，ボード名だけで指定できます（2.2節の解説）．

D.2 サンプルごとの注意

 

  • hello_world: ほぼすべてのボードでそのまま動きます．シリアルポートの名前やボーレートはボードによって異なることがあるので，各ボードのドキュメントを確認してください．
  • blinky: ボードのデバイスツリーにled0というエイリアスが定義されていれば，そのまま動きます（2.4節）．
  • thermometer: 温度センサーがボードに載っていて，そのセンサーをambient-temp0として指すオーバーレイが必要です．samples/sensor/thermometer/boards/に，使いたいボード向けの.overlayがあるか確認してください．無い場合は，3.3節で見たオーバーレイを参考に自分で書くことになります．
  • http_server: Ethernetを持つボードでなければ動きません．

また，west flashが使う書き込みツールは，ボードによって異なることがあります．Zephyr公式ドキュメントの各ボードのページ（「Supported Boards」からボード名で検索）で，対応している書き込みツールを確認してください．

付録F. よくある質問

 

Q. Zephyrは商用製品に使えますか？

A. Zephyr本体はApache License 2.0で公開されており，商用製品にも使えます．ただし，Zephyrと一緒に使うモジュール（外部ライブラリ）には別のライセンスのものもあるので，製品に組み込む際は，使っているモジュールのライセンスもあわせて確認してください．

Q. MCUXpresso SDKとZephyrは，どう使い分ければいいですか？

A. NXPのマイコンでは，どちらも使えます．MCUXpresso SDKはNXPのマイコン向けに提供されるドライバやサンプルのパッケージで，ベアメタルやFreeRTOSでの開発に向いています．Zephyrは，ボードやベンダーをまたいで同じ書き方・同じ手順で開発できることや，ネットワークなどのミドルウェアが豊富なことが強みです．既存の資産や，将来ほかのマイコンにも展開するかどうかで選ぶとよいでしょう．

Q. 今日はコマンドラインで操作しましたが，MCUXpresso for VSCでもできますか？

A. はい．MCUXpresso for VSCからも，Zephyrアプリケーションのビルドや書き込み，デバッグができます．本記事でコマンドラインを使ったのは，どのボード・どのベンダーでも共通の手順を体験してもらうためです（2.1節）．

Q. ブレークポイントを使ったデバッグはできますか？

A. できます．コマンドラインではwest debugでデバッガを起動できます．GUIで操作したい場合は，MCUXpresso for VSCを使うのが手軽です．

Q. 今日使ったZephyrのバージョンは？

A. 【会場PCのZephyrバージョンを記入】です．ボードの起動時にシリアルコンソールに表示される*** Booting Zephyr OS build v4.x.x ***の行でも確認できます．バージョンが違うと，サンプルの中身や出力が本記事と少し異なることがあります．

Q. WindowsではなくmacOSやLinuxでもできますか？

A. できます．環境構築は公式のGetting Started Guideを参照してください．コマンドの書き方は，付録Bにbash・zsh版をまとめています．

Q. printfの出力は，どうやってPCに届いているのですか？

A. マイコンのUART（シリアル通信）から出力された文字が，ボード上のMCU-Linkを経由して，USBの仮想COMポートとしてPCに届いています．そのため，書き込み用と同じUSBケーブル1本で，シリアルコンソールも使えます．

付録G. HTTP Serverサンプルの足回り

 

5章のリポジトリのsrc/main.cやCMakeLists.txtには，温度センサーの追加とは直接関係のない部分がかなりあります．HTTP Serverサンプルが，Webサーバーとして配信するデータ一式（トップページのHTML，JavaScript，LED制御・/uptime・ネットワーク統計といった元からある複数のエンドポイント）も，あわせて用意しているためです．ここでは，その「HTTPサーバーとして動くための足回り」を説明します．5章の手順を進めるだけなら，読まなくて構いません．

HTMLとJavaScriptの埋め込み

index.htmlやmain.jsは，CMakeLists.txtの中のgenerate_inc_file_for_target()によって，ビルド時にgzipで圧縮されます．圧縮したデータはindex.html.gz.incのようなファイルになり，main.cから#includeされて，プログラムの中に埋め込まれます．

エンドポイントの一覧

HTTP_RESOURCE_DEFINE()で登録した各エンドポイントは，sections-rom.ldというリンカスクリプトが用意する専用のセクション（http_resource_desc_test_http_serviceなど）に置かれます．HTTPサーバーは，起動時にこのセクションをたどって，エンドポイントの一覧を作ります．

このsections-rom.ldと，CMakeLists.txt側のzephyr_linker_sources()の対応が崩れると，_http_resource_desc_test_http_service_list_startのようなシンボルが見つからず，リンクエラーになります．
