## 1. Zephyrとは？

<a id="1-1"></a>
### 1.1 Zephyrの概要と特長

Zephyrは，Linux Foundation配下で開発が進むオープンソースのRTOS（リアルタイムOS）です．小規模なマイコンから比較的リソースの大きなSoCまで，幅広いハードウェアを対象にしています．対象範囲の広さはNXP製品だけを見ても分かりやすく，今回使うMCXシリーズのようなCortex-Mコアのマイコンから，i.MXシリーズのようなCortex-Aプロセッサを使うアプリケーションプロセッサまで，同じZephyrという1つのOSでカバーしています．マイコンからプロセッサまでを1つのRTOSで扱えるという点は，ボードごとにOSやビルド環境を使い分けなくて済むという実用上のメリットに直結します．

特長を一言でまとめると，「デバイスツリー」と「Kconfig」という2つの仕組みで，ハードウェア構成とソフトウェア機能の有効/無効を分離して管理できる点です．この分離のおかげで，同じアプリケーションコードを複数のボードに展開しやすくなっています．

言い換えると，C言語などで書くアプリケーションのロジックそのものは「何のセンサーが」「どのバスに」つながっているかを直接知らなくてよい，という設計になっています．ハードウェア構成はデバイスツリー，機能のオン/オフはKconfigというソフトウェア・モジュール側の設定に閉じ込められていて，アプリケーションのコードは`DEVICE_DT_GET`のようなAPIを通してデバイスにアクセスするだけです．この「アプリのロジック」と「ハードウェア・ソフトウェアモジュールの構成」の分離を，3章で実際のコードを見ながら体感します．

<a id="1-2"></a>
### 1.2 なぜ今Zephyrなのか

半導体メーカー各社が，既存製品ラインを含めZephyrへの対応を広げています．特定のベンダーに縛られないRTOSとして，業界内での存在感が増しているのが現状です．

Zephyrプロジェクト自体は2016年にLinux Foundation配下でスタートしており，今日でおよそ10年の歴史を持ちます．決して新しくて枯れていない技術ではなく，この間に積み重ねられてきたのは，CPUアーキテクチャやペリフェラルドライバだけではありません．今回4章・5章で体験するHTTP ServerのようなTCP/IPスタックやHTTPサーバーといったネットワーク関連のミドルウェアも，Zephyr本体に標準搭載されたサブシステムとして育ってきています．マイコン向けOSというと最小限のスケジューラ機能だけを想像しがちですが，こうした上位のミドルウェアまで一貫してKconfigで有効化できる点も，Zephyrを選ぶ理由のひとつです．

「結局何がそんなに良いのか」は，触ってみないと実感しにくい部分です．この記事では，実際に手を動かしながらその感触を確かめていきます．

<a id="1-3"></a>
### 1.3 FRDM-MCXN947について

FRDM-MCXN947は，NXPのMCX N947マイコンを搭載した評価ボードです．150MHzで動作するCortex-M33のデュアルコア構成で，GPIO・I2C・I3C・SPI・Ethernetなど様々なペリフェラルをArduinoヘッダ，MikroBusソケットほか様々なコネクタ経由で扱えます．

## 2. 開発環境を触ってみる

<a id="2-1"></a>
### 2.1 環境の確認

会場のPCには，west・Zephyr SDKを含む開発環境を，公式のGetting Startedガイドの手順に沿って，あらかじめコマンドライン中心にセットアップしてあります．このPCではMCUXpresso for VSCも利用できる状態になっていますが，このセミナーでは特定のチップベンダーに依存せず，どのターゲットボードでも共通の手順で扱えるという理由から，あえてコマンドラインでの操作を体験していただきます．皆さんに環境構築で手間取っていただく必要はありません．まずはターミナルを開いて，以下のコマンドでwestが使える状態になっていることを確認します．

> **コラム: 帰ってから自分の環境をセットアップするには**
> 今回は会場PCに環境構築済みの状態で臨んでいただいていますが，ご自身のPCでも同じ環境を用意できます．
> - 公式ガイド: [Getting Started Guide](https://docs.zephyrproject.org/latest/develop/getting_started/index.html)
> - NXPのツールを使った簡単セットアップ: [Zephyrシリーズ 第２回 はじめてのビルドと実機動作（NXP Tech Blog，日本語）](https://community.nxp.com/t5/NXP-Tech-Blog/Zephyr-シリーズ-第２回-はじめてのビルドと実機動作-日本語ブログ/ba-p/2189007)

【どのターミナルを使うか．操作方法も示しておく】

westコマンドを使う前に，Zephyr用のPython仮想環境と環境変数を読み込んでおく必要があります．以下の2行を実行してから`west --version`を実行してください．

```
source ~/zephyrproject/.venv/bin/activate
source ~/zephyrproject/zephyr/zephyr-env.sh
west --version
```

> **コラム: このコマンドで何をしているか**
> - `source ~/zephyrproject/.venv/bin/activate` — Zephyr用に用意されたPython仮想環境を有効化します．west自体やビルドに使う各種Pythonツールが，この仮想環境にインストールされています．
> - `source ~/zephyrproject/zephyr/zephyr-env.sh` — Zephyr SDKのパスなど，ビルドに必要な環境変数をシェルに読み込みます．
> - `west --version` — westコマンド自体が正しく使える状態になっているかを，バージョン表示で確認します．
>
> 本記事に登場する他のコマンドについても，同様に別枠でオプションや役割を解説していきます．

このターミナルは，セミナーの間は開いたままにしておいてください．この後の章でも使う`west`コマンドの実行に必要です．閉じてしまうと，環境変数の読み込みをし直さなければなりません．

### 2.2 HelloWorldサンプルを実行してみる

これ以降，サンプルコードは`zephyr/samples/`配下のものを直接編集するのではなく，受講者ごとの作業用フォルダにコピーしてから，そのコピーに対してビルド・書き込みを行います．`zephyr/samples/`配下は元のサンプル集として手を加えずに残しておき，実験や書き換えは自分のフォルダの中だけで完結させる，という進め方です．

まずZephyrに標準で含まれる`hello_world`サンプルコードを以下のコマンドでコピーし，そのディレクトリに移動します．

```
cp -r samples/hello_world ~/handson/hello_world
cd ~/handson/hello_world
```

> **コラム: 作業用フォルダへのコピーについて**
> `cp -r`で`zephyr/samples/`配下のサンプルを丸ごと自分の作業フォルダにコピーし，`cd`でそのフォルダに移動しています．以降の章でも同じように，触りたいサンプルをまず作業用フォルダへコピーしてから作業を始めます（この解説は，以降に登場する同様のコピー・移動コマンドにも共通です）．

このフォルダ内で`hello_world`をビルドします．

```
west build -p auto -b frdm_mcxn947/mcxn947/cpu0 .
```

> **コラム: `-b`・`-p`オプションについて**
> - `-b`に続く引数は，ビルド対象のターゲット基板の指定です．FRDM-MCXN947はCortex-M33のデュアルコア構成のため，`frdm_mcxn947/mcxn947/cpu0`のように基板名／SoC名／コア名まで指定する必要があります．FRDM-MCXA153のようなシングルコアの基板では，`frdm_mcxa153`という基板名だけで指定が済みます．なお，SoC名を省略して`frdm_mcxn947//cpu0`と書くこともできます．FRDM-MCXN947のようにSoCが1つしかない基板では，間のSoC名を省略してスラッシュだけを残しても一意に解釈できるためです．本記事でも2.3節以降はこの省略形を使います．
> - `-p auto`は`--pristine=auto`の省略形で，ビルドフォルダをクリーンな状態から作り直す（pristineビルドする）かどうかを自動判定するオプションです．`--pristine`については次のコラムで詳しく説明します．
> - 以降の章で登場する`west build`・`west flash`でも，これらのオプションの意味は共通です．

ビルドが完了すると，次のようなビルドの結果情報が表示されます．
エラーの場合はその情報が表示されます．ただし，Zephyrのエラー情報は大量になることが多く，最初はそれを追うのが大変です．エラーメッセージを注意深く読んだり，あるいはAIの力を借りて把握するのが良いでしょう．

ビルドの結果，ターゲットのマイコンに書き込むコードができました．以下のコマンドで書き込みます．

> **コラム: ビルド成果物の場所**
> ビルドが成功すると，カレントディレクトリに`build/`フォルダが作られます．書き込みに使われるのは`build/zephyr/zephyr.elf`（デバッグ情報付きのELFファイル）で，この後実行する`west flash`もこのファイルを使ってボードへの書き込みを行います．そのほか，コンフィグの内容は`build/zephyr/.config`，展開後のデバイスツリーは`build/zephyr/zephyr.dts`で確認できます．
> `--pristine`オプションは，このビルドフォルダを作り直すかどうかを指定するオプションです．`-p auto`（`--pristine=auto`）は，ソースやコンフィグの変更を検知して必要な時だけビルドフォルダを作り直します．ビルドの様子がおかしいときなど，明示的にクリーンビルドしたい場合は`-p always`（`--pristine=always`）を指定します．

【実行例のスクリーンショットを挿入】

`hello_world`の`src/main.c`は，次のように驚くほど短いコードです．VSCodeでこのファイルを開くには，作業用フォルダ（`~/handson/hello_world`）をVSCodeの「Open Folder」で開き，エクスプローラーから`src/main.c`を選択してください．ターミナルから`code ~/handson/hello_world`と実行して開くこともできます．

```c
#include <stdio.h>

int main(void)
{
	printf("Hello World! %s\n", CONFIG_BOARD_TARGET);

	return 0;
}
```

これを見る限り，至って普通のC言語による`Hello World`コードです．強いて特別な点を挙げるなら，`CONFIG_BOARD_TARGET`というマクロがこのビルド環境の中で定義されているのだろう，という程度です．マイコンプログラムでよく見られるクロック設定やペリフェラルの初期化処理は，このコードのどこにも見当たりません．

クロック設定やペリフェラル初期化がないという「マイコンのコードっぽくなさ」に加えて，タスク（スレッド）の生成もスケジューラの起動宣言も無いという「RTOSのコードっぽくなさ」も，このコードの特徴です．`main()`から`printf()`を呼ぶだけの，PC向けのC言語プログラムとほとんど同じ見た目になっています．多くのRTOSでは「Hello World」のために，タスクを明示的に作って`osKernelStart()`のような呼び出しでスケジューラを起動する，という手順が必要になりますが，Zephyrでは`main()`自体がすでに1つのスレッドとして動いており，その手前の初期化はビルドシステムとKconfigの設定に任されています．この「素のCプログラムに近い書き味」は，Zephyrがアプリケーション開発者に見せる顔の特徴のひとつです．

> **コラム: main.c以外に必要なファイル**
> Zephyrアプリケーションとして最低限必要なのは，`src/main.c`のほかに`prj.conf`と`CMakeLists.txt`の2つです．`prj.conf`は，そのアプリケーションで使うKconfig機能を列挙する設定ファイルで，`hello_world`では特に有効化したい機能がないため中身はほぼ空です．`CMakeLists.txt`は`find_package(Zephyr ...)`でZephyrのビルドシステムを読み込み，`target_sources()`でビルド対象のソースファイルを指定するビルド定義ファイルです．実際に`zephyr/samples/hello_world/`の中を見ても，ファイルは`CMakeLists.txt`・`prj.conf`・`src/main.c`（と説明用の`README.rst`）程度しかなく，Zephyrアプリケーションの最小構成がこの3点セットであることが確認できます．

<a id="3-3"></a>
### 3.3 なぜ動いたのか？

センサーの値がなぜ表示されたのか，`src/main.c`と`boards/*.overlay`を見ながら種明かしをします．

`main.c`側では，センサーデバイスを次のように取得しています．

```c
static const struct device *const temp_dev = DEVICE_DT_GET(DT_ALIAS(ambient_temp0));
```

この`ambient_temp0`というエイリアスが，実際にどのハードウェア（センサー品種・接続バス）を指すのかを決めているのが`boards/*.overlay`です．ここで初めて「デバイスツリー」という言葉が実感を伴って登場します．今回のFRDM-MCXN947では，温度センサーはI3Cバスにぶら下がっており，`boards/frdm_mcxn947_mcxn947_cpu0.overlay`には次のように定義されています（実際のファイルにはI3Cバスのクロック速度指定なども含まれますが，ここでは要点を抜粋しています）．

```dts
/ {
	aliases {
		ambient-temp0 = &p3t1755;
	};
};

&i3c1 {
	status = "okay";

	p3t1755: p3t1755@4800000236152a0090 {
		compatible = "nxp,p3t1755";
		reg = <0x48 0x0236 0x152a0090>;
		status = "okay";
	};
};
```

`aliases`ブロックで`ambient-temp0`を`p3t1755`ノードに結び付け，`i3c1`バス配下に`nxp,p3t1755`ドライバを持つセンサーノードを1つ生やしているだけです．`main.c`側は`DT_ALIAS(ambient_temp0)`としか書いていないので，このセンサーがI2Cではなく（より高速な）I3Cで繋がっていることも，レジスタアドレスの詳細も，アプリケーションコードは一切知りません．

コードを一行も書かずに，「デバイスツリーの定義を変えるだけで別のハードウェア構成に対応できる」というのがここでの見どころです．たとえば同じセンサーをI2C接続のボードに載せ替えたり，別の温度センサーIC（対応ドライバがある前提）に変更したりする場合でも，変更するのは基本的に`boards/*.overlay`の中だけで，`main.c`の`DEVICE_DT_GET(DT_ALIAS(ambient_temp0))`という1行はそのまま使い回せます．

> **コラム: デバイスツリーの実体はどこにあるのか**
> 1. `main.c`にはアプリケーションのロジック（センサーを読んで表示するという処理）だけが書かれ，ハードウェアの接続情報はデバイスツリーに切り出されています．FRDM-MCXN947のボード自体が持つデバイスツリーの本体は，Zephyr本体側の`zephyr/boards/nxp/frdm_mcxn947/frdm_mcxn947_mcxn947_cpu0.dts`（および共通定義の`frdm_mcxn947.dtsi`）です．ここにはボードに標準搭載されたペリフェラル一式が定義されています．
> 2. とはいえ，このボード本体のデバイスツリーファイルを直接書き換えることはしません．Zephyrでは，アプリケーション側（`samples/sensor/thermometer/boards/frdm_mcxn947_mcxn947_cpu0.overlay`，5章で使うこのハンズオン用リポジトリでは`boards/frdm_mcxn947_mcxn947_cpu0.overlay`）に，ボード本体の定義へ**追記・上書きするための差分ファイル**である「デバイスツリーオーバーレイ」（`*.overlay`）を置く，という作法を取ります．本文中に示した`p3t1755`ノードの定義も，このオーバーレイファイルの中身です．ボード本体の定義はそのままに，アプリケーションごとに必要な差分だけを重ねられるのが利点です．
> 3. ビルドを実行すると，ボード本体のデバイスツリーとアプリケーションのオーバーレイがマージされ，最終的に使われるデバイスツリー全体が`build/zephyr/zephyr.dts`というファイルに書き出されます．このファイルを開くと，`p3t1755`ノードがボード本体の定義に追加された状態でマージ済みであることが実際に確認できます．「デバイスツリーが変更された結果」を自分の目で見たいときは，このファイルを覗いてみてください．
>
> OSを使わないベアメタル開発や，デバイスツリーの仕組みを持たない多くのRTOSでは，センサーのI2C/I3Cアドレスやレジスタ操作をアプリケーションコードの中に直書きするのが一般的です．そのため，センサーの型番やバス配線が変わるたびに，アプリケーションロジックの書き換えとリビルドが必要になります．Zephyrでは，この「どの部品が」「どこに」繋がっているかという情報をデバイスツリーという別レイヤーに追い出しているため，ボードが変わってもアプリケーションのロジック（この場合は「気温を読んで表示する」という処理）そのものは触らずに済みます．今回のセミナーでは時間の都合でここまで深入りしませんが，興味を持った方はぜひ他のボード向け`overlay`ファイルも見比べてみてください．同じ`samples/sensor/thermometer`でも，ボードごとにハードウェア接続だけが違う`overlay`が用意されていることが分かるはずです．

### 4.1 サンプルをビルド・書き込む

`samples/net/sockets/http_server`をビルド・書き込みします．今回はTLSを使わないプレーンHTTP・固定IP接続で進めます．

> **コラム: なぜプレーンHTTPを使うのか**
> プレーンHTTPは，通信内容が暗号化されないHTTP通信です．実運用では，通信内容の盗聴や改ざんを防ぐため，TLSで暗号化されたHTTPS通信の利用が推奨されます．HTTPSを使うには，サーバー証明書や秘密鍵といった認証まわりのファイルをあらかじめ用意する必要があります．Zephyrでも，こうした認証の仕組みや，通信そのものを暗号化する仕組みはサポートされています．しかし今回のハンズオンでは，限られた時間の中で認証ファイルの準備といった手間を省き，HTTP Serverそのものの仕組みを体験することに集中するため，あえてプレーンHTTPを使います．

このサンプルコードも作業用フォルダにコピーして進めます．

```
cp -r samples/net/sockets/http_server ~/handson/http_server
cd ~/handson/http_server
```

コピーが済んだら`prj.conf`ファイルに変更を加えます．
基板に固定IPアドレスを持たせるため`CONFIG_NET_CONFIG_MY_IPV4_ADDR`，`CONFIG_NET_CONFIG_MY_IPV4_GW`，`CONFIG_NET_CONFIG_MY_IPV4_NETMASK`が書かれてある3行を探し，それを次のように変更します．

```
CONFIG_NET_CONFIG_MY_IPV4_ADDR="192.168.1.100"
CONFIG_NET_CONFIG_MY_IPV4_GW="192.168.1.1"
CONFIG_NET_CONFIG_MY_IPV4_NETMASK="255.255.255.0"
```

> **コラム: Gatewayの設定について**
> Gateway（`CONFIG_NET_CONFIG_MY_IPV4_GW`）は，ルーターを経由しない通信では本来必須ではありません．今回はPCとボードをEthernetケーブルで直結し，同じ`192.168.1.0/24`のサブネットに両方を置くので，通信はすべて同一リンク内のARPで解決され，Gatewayを経由するルーティングは発生しないためです．

会場のPC側のIPアドレスは，あらかじめこのボードと同じ`192.168.1.0/24`のサブネットに収まるよう設定済みです．PC側の設定を変更する必要はありません．

### 4.2 ブラウザからLEDを制御してみる

ブラウザで`http://<ボードのIPアドレス>/`にアクセスすると，LED制御用のページが表示されます．ボタン操作でボード上のLEDが点灯/消灯することを確認します．

> **コラム: ネットワーク機能の「重さ」について**
> 一般的な組み込み開発では，HTTPサーバーを1つ動かすだけでも，TCP/IPスタック（lwIPなど）の組み込み・設定，ソケットAPIの用意，HTTPパーサーの選定・実装，静的ファイルの配信方法の実装，と多くの下準備が必要になりがちです．今回はそれらがすべて`prj.conf`の`CONFIG_NET_*`・`CONFIG_HTTP_*`系オプションを`y`にするだけで揃っており，アプリケーション側で書いたのは各エンドポイントのハンドラ関数だけです．ネットワークスタックからHTTPサーバーまでを1つのビルドシステムとKconfigで一貫して扱えるのは，Zephyrがマイコン向けRTOSでありながら比較的大きなミドルウェア込みで語られる理由のひとつです．

> **コラム: ZephyrのTCP/IPスタックはlwIPなのか**
> 組み込み向けのTCP/IPスタックというと，lwIP（lightweight IP）を思い浮かべる方も多いかもしれません．しかしZephyrは，lwIPを外部から取り込む形ではなく，`subsys/net/`以下に実装された独自のネイティブなTCP/IPスタックを標準で使っています．IPv4/IPv6・TCP/UDP・ソケットAPIといった機能がZephyr本体に組み込まれており，今回`prj.conf`で有効化した`CONFIG_NET_IPV4`や`CONFIG_NET_TCP`，`CONFIG_NET_SOCKETS`といったオプションも，このネイティブスタックの機能を指しています．（Zephyrはモジュールとして外部のネットワークスタックを組み合わせる構成にも対応していますが，本記事で使っているのは標準のネイティブスタックです．）

<a id="4-3"></a>
### 4.3 /uptimeエンドポイントを覗いてみる

`http://<ボードのIPアドレス>/uptime`にアクセスすると，ボードの起動からの経過時間が返ってきます．この「GETリクエストに対して，値を計算してテキストで返す」という一番シンプルなエンドポイントの作りを，次の5章でそのまま応用します．

> **コラム: HTTPリクエストとレスポンス**
> ブラウザで`/uptime`にアクセスすると，ブラウザからボードへ「このパスの内容をください」という意味の`GET`リクエストが送られます．ボード側では，リクエストを受け取ったHTTP Serverが，`/uptime`に紐づけられたハンドラ関数（`uptime_handler`）を呼び出します．ハンドラは起動からの経過時間を計算し，その値をレスポンスの本文（body）としてセットします．HTTP Serverはこの本文に，ステータス行（`200 OK`など）やヘッダーを付け加えたHTTPレスポンスとして，ブラウザに返します．ブラウザは受け取ったレスポンスの本文をそのまま画面に表示します．5章で追加する`/temperature`エンドポイントも，リクエストを受けて値を計算し，本文として返すという，全く同じ流れで動いています．

## 5. HTTP Serverを改変して，温度センサーの値をブラウザで見る

<a id="5-1"></a>
### 5.1 何を追加したか

4.3で見た`/uptime`エンドポイントと同じ作りで，`/temperature`エンドポイントを追加しました．変更は`src/main.c`のごく一部です．

```c
static int temperature_handler(struct http_client_ctx *client, enum http_transaction_status status,
                const struct http_request_ctx *request_ctx,
                struct http_response_ctx *response_ctx, void *user_data)
{
    /* 3章の温度センサーと同じ device_get / sensor_sample_fetch_chan /
       sensor_channel_get の流れで気温を取得し，HTMLとして返す */
    ...
}
```

追加したのは，この`temperature_handler`と，それを`/temperature`というパスに紐づける1行だけです．他の部分（LED制御，`/uptime`，静的ページ配信）は元のサンプルのまま変更していません．

<a id="5-2"></a>
### 5.2 実際にブラウザで表示してみる

ブラウザで`http://<ボードのIPアドレス>/temperature`にアクセスすると，その時点の気温がHTMLで表示されます．

【画面キャプチャを挿入：Temperature: XX.XXX°C】

<a id="5-3"></a>
### 5.3 3章・4章の内容がどう組み合わさっているか

3章で動かした温度センサーの読み取りコードと，4章で動かしたHTTP Serverの仕組みを組み合わせただけ，というのがこのステップの種明かしです．それぞれ単体で理解した部品を組み合わせると，ブラウザからセンサー値を見るというアプリケーションになる，という流れを振り返ります．

> **コラム: main.cとCMakeLists.txtが少し煩雑に見える理由**
> 実際に`src/main.c`を開くと，`/temperature`ハンドラ以外にもかなりの行数があることに気づきます．これは，このHTTP Serverサンプルが「Webサーバーとして配信するデータ一式（トップページのHTML，JavaScript，LED制御・uptime・ネットワーク統計といった元からある複数のエンドポイント）」もあわせて用意しているためです．特に，`index.html`や`main.js`は`CMakeLists.txt`内の`generate_inc_file_for_target()`によってビルド時にgzip圧縮され，`index.html.gz.inc`のようなCヘッダとして`main.c`から`#include`される形で埋め込まれています．また，`HTTP_RESOURCE_DEFINE()`で登録した各エンドポイントは，`sections-rom.ld`というリンカスクリプトが用意する専用のセクション（`http_resource_desc_test_http_service`など）に配置されることで，HTTPサーバーが起動時にエンドポイント一覧を辿れるようになっています．この`sections-rom.ld`と`CMakeLists.txt`側の`zephyr_linker_sources()`の対応が崩れると，`_http_resource_desc_test_http_service_list_start`のようなシンボルが見つからずリンクエラーになります．これらは温度センサーの追加そのものとは直接関係のない「HTTPサーバーを名乗るために必要な足回り」なので，今回はそういうものだと割り切って，`temperature_handler`と`temperature_json_handler`の中身だけに注目してもらえれば十分です．

### 6.3 AIをどう活用できるか

Zephyrのサンプルコードを読む・改変する際，AIアシスタントに「このサンプルにこういう機能を足すには」と相談すると，既存コードのパターンに沿った改変案を提示してもらえます．今回の`/temperature`エンドポイントも，既存の`/uptime`エンドポイントと同じ構造で追加しています．わからない箇所があれば，まず既存のサンプルコードの近い部分を探し，AIと一緒に読み解いてみることをおすすめします．

もう一つよくあるのが，`west build`でエラーになったときです．Zephyrのビルドエラーは，Kconfigの警告からCMakeのエラー，リンカのエラーまで一度に大量のメッセージが出力され，どこが本質的な原因なのか初見では分かりにくいことがあります．そんなときも，エラーメッセージ全体をそのままAIに貼り付けて「これはどういうエラーですか」と聞いてみるところから始めるのがおすすめです．本記事の4〜5章で登場した`sections-rom.ld`まわりのリンクエラーも，実際にはこの記事を書く過程でAIと一緒に原因を特定したものです．
